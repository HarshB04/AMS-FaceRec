# 📦 AMS-FaceRec — Database Schema Guide

> This document explains the database schema used in **schema.sql**, why each table exists, and how the frontend consumes the data.

---

## Why Supabase + PostgreSQL?

We chose **Supabase** as our backend because:

| Reason | Detail |
|---|---|
| **Hosted PostgreSQL** | No need to manage a database server ourselves — Supabase gives us a full Postgres instance in the cloud. |
| **Built-in Auth** | `auth.users` handles sign-up, login, sessions, and JWT tokens out of the box. Our `LoginPage.tsx` calls `supabase.auth.signInWithPassword()` directly. |
| **REST API auto-generated** | Every table we create automatically gets a REST endpoint via PostgREST. We access it through Supabase Edge Functions (`/functions/v1/server`). |
| **Row Level Security (RLS)** | We can lock down who reads/writes each row using Postgres policies — critical for a multi-role system (admin, teacher, student). |
| **Free tier** | Generous free tier for a college project — 500 MB database, 50K monthly active users. |

## Table-by-Table Breakdown

### 1. `students`

```sql
CREATE TABLE students (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    student_id_text TEXT UNIQUE,
    name TEXT NOT NULL,
    email TEXT UNIQUE NOT NULL,
    course TEXT,
    face_enrolled BOOLEAN DEFAULT FALSE,
    status TEXT DEFAULT 'active' CHECK (status IN ('active', 'inactive')),
    attendance_rate FLOAT DEFAULT 0,
    registration_date DATE NOT NULL DEFAULT CURRENT_DATE
);
```

**Why it exists:** This is the core table — every student in the system lives here.

| Column | Purpose |
|---|---|
| `id` | Auto-incrementing primary key. The frontend converts this to a string with `String(s.id)`. |
| `student_id_text` | A human-readable ID like `"STU-001"`. Displayed in the UI's student management table. Unique so no duplicates. |
| `name` | Student's full name. `NOT NULL` because we always need a name to display. |
| `email` | Used for login and communication. `UNIQUE` to prevent duplicate accounts. |
| `course` | Which course the student is enrolled in. Stored as plain text for simplicity (not a foreign key). |
| `face_enrolled` | `true/false` — whether the student has completed face recognition enrollment via the Python OpenCV engine. The frontend shows a badge for this. |
| `status` | `'active'` or `'inactive'`. The `CHECK` constraint prevents any other value from being inserted. Used to filter active students in dashboards. |
| `attendance_rate` | A cached percentage (0–100) of attendance. Updated periodically. Avoids computing it from the `attendance` table on every page load. |
| `registration_date` | Defaults to today's date. Used in reports and student profiles. |

**How the frontend uses it:**
- `api.ts` → `getStudents()` fetches all rows and maps `student_id_text` → `studentId`, `face_enrolled` → `faceEnrolled`, `attendance_rate` → `attendance`.
- `StudentManagement.tsx` displays the full table with CRUD operations.

### 2. `courses`

```sql
CREATE TABLE courses (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    course_name TEXT NOT NULL,
    course_code TEXT UNIQUE NOT NULL,
    teacher TEXT,
    schedule TEXT,
    room TEXT,
    student_count INT DEFAULT 0,
    status TEXT DEFAULT 'active'
);
```

**Why it exists:** Represents each class/course offered. Teachers and admins manage these.

| Column | Purpose |
|---|---|
| `id` | Auto-incrementing primary key. |
| `course_name` | Full name, e.g. `"Introduction to Computer Science"`. |
| `course_code` | Short unique code, e.g. `"CS101"`. Used as a quick identifier in dropdowns and attendance logs. |
| `teacher` | Name of the assigned teacher (stored as text). |
| `schedule` | Free-text schedule info, e.g. `"Mon/Wed 10:00 AM"`. |
| `room` | Room number/location. |
| `student_count` | Cached count of enrolled students. Avoids a `COUNT(*)` query each time. |
| `status` | `'active'` by default. Can be set to `'inactive'` to archive a course. |

**How the frontend uses it:**
- `api.ts` → `getCourses()` maps `course_name` → `name`, `course_code` → `code`.
- `AdminCourses.tsx` shows the course management grid.
- The `attendance` table references courses via `course_id`.

---

### 3. `attendance`

```sql
CREATE TABLE attendance (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    student_id BIGINT REFERENCES students(id),
    course_id BIGINT REFERENCES courses(id),
    date_attended DATE NOT NULL DEFAULT CURRENT_DATE,
    status TEXT DEFAULT 'absent' CHECK (status IN ('present', 'absent', 'late'))
);
```

**Why it exists:** This is the **heart of the system** — it logs every attendance event. One row = one student in one class on one day.

| Column | Purpose |
|---|---|
| `id` | Auto-incrementing primary key. |
| `student_id` | Foreign key → `students(id)`. Links this record to a specific student. |
| `course_id` | Foreign key → `courses(id)`. Links this record to a specific course. |
| `date_attended` | The date of the attendance event. Defaults to today. |
| `status` | `'present'`, `'absent'`, or `'late'`. The `CHECK` constraint enforces only these three values. Defaults to `'absent'` — a student is absent unless the face recognition system marks them otherwise. |

**How the frontend uses it:**
- `api.ts` → `logAttendance()` creates a new record when the Python face recognition engine detects a student.
- `AttendanceReports.tsx` reads all records to generate charts and reports.
- The `LiveCamera` page triggers attendance logging in real-time.

**How the face recognition flow works:**
1. Camera feed → Python OpenCV engine detects a face.
2. Engine matches face to a student → calls the Flask API bridge.
3. Flask API calls Supabase Edge Function → inserts a row into `attendance` with `status = 'present'`.

---

### 4. `instructors`

```sql
CREATE TABLE instructors (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name TEXT NOT NULL,
    email TEXT UNIQUE NOT NULL
);
```

**Why it exists:** Stores teacher/instructor profiles separately from `auth.users`. This table holds the **profile data**, while `auth.users` handles **authentication**.

| Column | Purpose |
|---|---|
| `id` | Auto-incrementing primary key. |
| `name` | Instructor's full name. |
| `email` | Unique email. Can be cross-referenced with `auth.users` email for linking auth to profile. |

**How the frontend uses it:**
- `api.ts` → `getInstructors()` fetches the list for the admin's teacher management page.
- `AdminTeachers.tsx` provides CRUD operations for instructor profiles.

---

### 5. `course_instructors` (Junction Table)

```sql
CREATE TABLE course_instructors (
    course_id BIGINT REFERENCES courses(id),
    instructor_id BIGINT REFERENCES instructors(id),
    PRIMARY KEY (course_id, instructor_id)
);
```

**Why it exists:** This is a **many-to-many join table**. One instructor can teach multiple courses, and one course could have multiple instructors.

| Column | Purpose |
|---|---|
| `course_id` | FK → `courses(id)`. |
| `instructor_id` | FK → `instructors(id)`. |
| Composite PK | `(course_id, instructor_id)` prevents duplicate assignments. |

**How it works:**
- To assign Dr. Smith (instructor `id=3`) to CS101 (course `id=7`):
  ```sql
  INSERT INTO course_instructors (course_id, instructor_id) VALUES (7, 3);
  ```
- To find all courses for an instructor:
  ```sql
  SELECT c.* FROM courses c
  JOIN course_instructors ci ON c.id = ci.course_id
  WHERE ci.instructor_id = 3;
  ```

## Key Design Decisions

### Why `BIGINT GENERATED BY DEFAULT AS IDENTITY` instead of `UUID`?

- Supabase supports both, but `BIGINT` identity columns are:
  - Simpler to read in logs (`id = 42` vs `id = 'a1b2c3d4-...'`).
  - Slightly faster for joins and indexing.
  - `GENERATED BY DEFAULT` means Postgres auto-assigns the next number, but you can also manually specify an ID if needed (unlike `GENERATED ALWAYS`).

### Why store `attendance_rate` and `student_count` directly?

- These are **denormalized/cached values**. Normally you'd compute them:
  ```sql
  -- Computed attendance rate
  SELECT (COUNT(*) FILTER (WHERE status = 'present') * 100.0 / COUNT(*))
  FROM attendance WHERE student_id = ?;
  ```
- But running that on every dashboard load is expensive. Instead, we store the result and update it periodically — a classic **read-heavy optimization**.

### Why `CHECK` constraints?

```sql
status TEXT CHECK (status IN ('active', 'inactive'))
status TEXT CHECK (status IN ('present', 'absent', 'late'))
```

- These act as **enums at the database level**. If the frontend accidentally sends `status = 'here'`, Postgres will reject it with an error instead of silently saving bad data.

### Why `teacher` is TEXT in `courses` and not a FK?

- For simplicity in the current version. The `teacher` column stores the teacher's name directly. The `course_instructors` junction table provides the proper relational link when needed. A future improvement would be to drop the `teacher` column and always join through `course_instructors`.

## How to Apply This Schema

### Option 1: Supabase SQL Editor (Recommended)

1. Go to your Supabase Dashboard → **SQL Editor**.
2. Paste the contents of `supabase/schema.sql`.
3. Click **Run**.

### Option 2: Supabase CLI

```bash
supabase db reset   # Drops and recreates from migrations
# or
supabase db push    # Applies new migrations
```

### Option 3: Direct psql connection

```bash
psql "postgresql://postgres:[password]@db.[project-ref].supabase.co:5432/postgres" \
  -f supabase/schema.sql
```
